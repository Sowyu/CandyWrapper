The user's definition, 2026-10-10: two halves, both required. - Re-pin to the then-current Nightly first (`T3_VERSION`, source fetch) so new Nightly behavior gets checked too.

## Findings worth knowing before you code

- Notifications (2026-10-11): usernoted refuses `UNUserNotificationCenter` authorization ("Failed to find or validate client") for a Debug build run from /tmp. A copy outside /tmp, re-signed with `codesign --force --deep -s -` (which adds a cdhash designated requirement) and registered with `lsregister -f`, works; give the test copy its own bundle id (`PRODUCT_BUNDLE_IDENTIFIER=dev.candywrapper.notifytest`) so its permission and UserDefaults stay apart from the user's demo app. Unregister it afterwards (`lsregister -u`).
- Long-thread updates and the disk cache (2026-10-10): T3 re-derives timeline rows per update but reuses entries and patches a streaming answer's rows in place (`deriveTimelineEntriesFromVisibleTurnItemsWithState`, session-logic.ts:930-1030; `replaceStreamingMessageRows`, MessagesTimeline.logic.ts:2058-2145), keeps unchanged row objects (`computeStableMessagesTimelineRows`) and virtualizes with LegendList. We do the same in `TimelinePipeline` (entries memoized per row, streaming patch, full pass otherwise), run it off the main thread at 1,500+ visible rows, and hand the timeline only the changed rows (`TimelineChange`). T3's thread cache is IndexedDB `t3code:connection-runtime`, store `thread`, key `env:thread`, value `{schemaVersion 3, environmentId, threadId, snapshot}`, written only when no run is preparing, starting or running and no older pages were loaded, first after 500 ms then at most every 10 s, removed on thread deletion and environment removal, no size limit; the cached `snapshotSequence` seeds `afterSequence` (threads.ts:90-330). Ours: `T3Store/ThreadCache.swift`. Swift array `==` short-circuits on shared storage, so comparing an untouched projection array is O(1); a COW copy of a 2,700-row array costs about 0.5 ms.

- Thread open (2026-10-10): T3's bounded snapshot caps the timeline window (10 user turns, 75 rows) but sends every run, attempt, node, checkpoint, request and provider turn of the thread (`buildBoundedThreadProjection`, threadHistoryPaging.ts:458), about 9 KB per run. A 900-run thread is an 8.3 MB frame however little it shows; T3's web client receives the same bytes. Most of our cost was turning JSONSerialization's tree into `JSONValue` (63 of 87 ms; now CF type ids and direct UTF-8 copies, 28 ms). Mutating a copy of an array's last element while the array still holds it copies the whole thing: `MarkdownDocument`'s tree builder did that per run, 302 ms for a reply of 2,400 short lines (now 34 ms). T3 paints a reopened thread from a 5-minute retained snapshot or its disk cache before any network; we now retain the last 2 closed thread stores for 5 minutes (about 12 MB each for a 900-run thread) and have no disk cache. Measure with `CANDY_THREAD_TIMING=1` (docs/perf/README.md).
- Perf measurement: scroll events posted to an app's PID (`CGEvent.postToPid`) never reach AppKit, and HID-tap events move the user's pointer, so the app scrolls itself with `--perf-scroll`. Package idle wakeups depend on what the whole machine does at that moment; compare idle numbers interleaved, not against a run from another hour.
- On-screen only bugs that offscreen snapshots miss: AppKit records `draw(_:)` and replays it at 2x, so a clip rect with an unbounded height became an empty clip (diff code never showed). `NSView.prepareForReuse()` unhides the view, so hide after calling it. Views drawn with the onSetNeedsDisplay policy keep their old image on resize unless marked for display (DSView now does that). Grain at 3.5% opacity sits under the 8/255 fidelity threshold, so grain bugs need their own check. Verify on screen with `screencapture` and `scripts/ui/`.
- DS menus: radio items only call `onToggle`; set `closesOnClick` to run `action` and close (base-ui `closeOnClick`).
- `NSView.prepareForReuse()` unhides the view and sets alpha to 1. Call it before hiding a recycled view. The timeline did it the other way round, and every recycled row stayed on screen at its old frame (the doubled and misplaced rows on the user's live thread, 2026-10-10). `TimelineView.layoutProblems()` checks the tiling contract; the hidden Cmd+Opt+Shift+L menu item writes it for the live app to `/tmp/cw-timeline-<pid>.txt`.

- Memory: a view that draws (`wantsUpdateLayer` false) gets a backing store of its full size, 8 bytes per pixel at 2x on this screen, so a window-sized one costs 27 MB plus the same again in CG scratch. Use layer properties for fills (`GrainSurfaceView` is a background color plus replicated tiles). Since macOS 14 views don't clip their drawing, and drawing outside the bounds grows the backing store, up to the whole window: set `clipsToBounds = true` (the setter, not an override) on views that draw off-canvas tricks, and give transparency layers explicit rects. To find the cause: `footprint -p`, `vmmap -summary`, `MallocStackLogging=1` with `malloc_history -allEvents`, and a dump of the window's layer tree looking for big layers with contents.
- Debug builds are ad-hoc signed (designated requirement is the cdhash), and tokens live in the file-based login Keychain. Each rebuild is a new app to the Keychain: reading a token saved by an older build prompts the user, and from an SSH-launched process the read likely fails instead. So after a rebuild `scripts/run-app --live` may show the pairing sheet again, and each Connect adds a device record to `~/.t3`. Keep live runs rare. A Developer ID build (M9) has a stable requirement. Keychain calls run off the main thread so a prompt can't freeze the window.
- `NSApp.terminate` called from inside a main-queue block (`asyncAfter`, a main-actor Task) runs AppKit's terminate loop inside that block. With `.terminateLater`, a reply that waits on main-actor work deadlocks. `ServerController.shouldTerminate` decides synchronously, shuts down in a detached task and replies with `CFRunLoopPerformBlock`.
- The harness kills a background command's whole process tree at its time limit, setsid children included. Use `scripts/run-app` with `--snapshot` so the app quits on its own, and give background runs a long timeout.
- `~/.local/bin/t3` points at runtime 0.0.45; the live service runs the nightly named in `~/.t3/runtime/service-state.json`. `LocalServerDiscovery.resolveBinary` prefers service-state, then PATH.
- The app-owned server logs stderr to `~/Library/Logs/CandyWrapper/t3-server.log`.

- WebSocket endpoint is `GET /ws?orchestrationProtocol=2&wsTicket=...`. Missing or wrong protocol version gives HTTP 426.
- Framing is Effect RPC JSON: one JSON message or a JSON array of messages per text frame. Client sends `Request`, `Ack`, `Interrupt`, `Ping`, `Eof`. Server sends `Chunk`, `Exit`, `Defect`, `Pong`, `ClientProtocolError`.
- The server waits for an `Ack` after every `Chunk` before sending the next chunk of that stream.
- Pairing is an OAuth token exchange at `POST /oauth/token` (form encoded), then `POST /api/auth/websocket-ticket` with the bearer token. Pairing tokens expire after 5 minutes. Access tokens last 30 days.
- Authenticated HTTP needs the header `x-t3-orchestration-protocol: 2` or it returns 400.
- `WS_METHODS` in `packages/contracts/src/rpc.ts` lists names the server does not serve, for example `projects.list`. The real list is the `WsRpcGroup` at rpc.ts:1811.
- For the Claude provider, assistant text arrived as one complete `message.updated`. Reasoning text streamed as full-text snapshots every few seconds, not deltas. Plan incremental Markdown around full-text replacement.
- `server.getConfig` is about 80 KB and includes providers, models and keybindings.
- Idle sandbox server: `t3` 0.14% CPU, about 10.7 interrupt wakeups per second, 205 MB footprint. An attached idle `claude` session adds 0.45% CPU and 10 wakeups per second.

A printing loop on the normal screen does the same and `less` (alternate screen, no redraws) does not, so steady redrawing is the trigger. vmmap puts the extra 48 MB in `owned unmapped (graphics)`: macOS draws a large view that keeps redrawing on the GPU and holds about 50 MB per process until redraws stop for about 5 s.
