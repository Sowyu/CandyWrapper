# Bring-up on the Mac mini M2 Pro, 2026-11-19

This is the first build of CandyWrapper on the Mac mini M2 Pro (Mac14,12, 32 GB, macOS 27.2.1, user `administrator`, uid 501). Only the Command Line Tools are installed, with Swift 6.4.2. Xcode is not.

## What builds

- `swift build` in `Packages/CandyKit` passes in 58 seconds. The linker warns that `/Library/Developer/CommandLineTools/Developer/Library/Frameworks` doesn't exist, which is harmless.
- `xcodegen` 2.46.0 regenerates `CandyWrapper.xcodeproj` byte-identical to the checked-in project. It doesn't need Xcode.
- The app target doesn't build, because `xcodebuild` needs Xcode. `scripts/build-test-app`, `scripts/run-app`, `scripts/perf-review`, `scripts/release` and `scripts/build-helper` wait on it too.
- `swift test` fails to compile DesignSystemTests, since three of its files import XCTest and the Command Line Tools ship only Swift Testing: `CandyThemeBaselineTests.swift`, `ThemePaletteTests.swift` and `ThemeRuntimeTests.swift`. Every other test file uses Swift Testing. `scripts/test --fast` fails the same way, so on this Mac neither runs until Xcode is installed.

## Test baseline

I set the three XCTest files aside in a scratch worktree, `/tmp/cw-bringup` at `97baaa2e`, and ran the full `scripts/test` there. The full run took about 6 minutes after the build.

- 2,481 Swift Testing tests ran in seven targets.
- 2,475 passed and 6 failed with 11 issues, all in FeaturesTests.
- 36 tests and suites were skipped, mostly the opt-in integration suites that `scripts/test-integration` runs.
- All 59 fidelity suites passed, so the fonts and references in the repo are enough. They use system fonts only.
- The 19 XCTest tests in the three set-aside files didn't run.

The failing tests and their first error lines:

1. `RedesignBaselineTests.exactPixels()`: "sidebar-many-threads.light: 1992 pixels differ (threshold 0)", and the dark case with 2,098.
2. `SidebarDitherRowTests.waitingRowShowsTheDotGridWithoutItsWord()`: "Expectation failed: content.list.rowView("thread:q1") as? SidebarCardRowView" at `SidebarDitherRowTests.swift:29`.
3. `SidebarProviderStackTests.redesignRowsPutTheStackAtTheBottomRight(dark:)`: the same missing row view at `SidebarProviderStackTests.swift:54`, light and dark.
4. `OrchestratorThreadRowTests.threadRowsLookTheSameWithTheToggleOnAndOff(dark:)`: the same missing row view at `OrchestratorThreadRowTests.swift:40`, light and dark.
5. `SidebarMultiMachineTests.sameLocalIdsOnThreeMachinesStayApart()`: "Expectation failed: Set(rows.map(\.id)) == ..." at `SidebarMultiMachineTests.swift:98`.
6. `SidebarLoadTests.contentViewPatchesTheList()`: "Expectation failed: cache.generation == generation" at `SidebarLoadTests.swift:71`.

All six fail the same way when run alone. None of them comes from missing Xcode, fonts or references.

The Redesign baseline fails because of this Mac's account. The sidebar footer draws `NSFullUserName()` (`SidebarChromeViews.swift:564`), and the baseline images show "mrm". The diff covers only the name and its initials. The test needs a fixed name injected, or new baselines on whichever Mac is canonical.

The five sidebar tests fail because they depend on saved state. `SidebarContentView` reads `ClientSettingsStore.shared`, which keeps `clientSettings.v1` in `UserDefaults.standard`. Under `swift test` that is the `swiftpm-testing-helper` domain, which persists between runs. Since `a5bf927e` on 2026-10-28, `sidebarWorkingShelfEnabled` defaults to true, so these tests' working threads move into the Working shelf and their card rows never appear. When I wrote `sidebarWorkingShelfEnabled = false` into that domain, all 14 tests in the five suites passed. Afterwards I put the domain back as the test run had left it.

The old Mac most likely still keeps a false value from before that commit, which hides the bug there. This is a real test-isolation bug: the tests should set the shelf off themselves or use an ephemeral settings store. On this Mac they fail on every run until someone fixes it. I didn't fix it, since this task only covers scripts.

One rerun failed to compile AgentConfigTests with "plugin for module 'TestingMacros' not found", and the next identical run built fine. Treat it as a one-off failure loading the Command Line Tools plugin.

## Script fixes

Most scripts already detect the user and uid with `id -un` and `id -u`, and the sandbox paths come from `$HOME`. I changed only what was wrong here.

- `scripts/preflight` used the zsh glob `/tmp/cw-*`, which aborts with "no matches found" when no build exists. It now uses `(N)` and passes `/dev/null` so `du` never sizes the current folder.
- `scripts/sandbox-server` now honors `T3_BIN`, which `docs/nightly-catch-up.md` already told agents to pass. Without it the script picks the live T3's copy in `~/.t3/runtime/versions` whenever the live T3 has that version, as it has 4928 here.
- 19 generator scripts defaulted to `/Users/mrm/CandyWrapper-research`. They now expand `~/CandyWrapper-research`, so both Macs work. Test strings that only mention `/Users/mrm` stay as they are.

`scripts/run-app` and the html-benchmark scripts call `sudo launchctl asuser`. sudo asks for a password on this Mac, so they stop at the prompt. I left them alone because the app can't build yet.

## ~/CandyWrapper-research

- `tools/xcodegen` holds XcodeGen 2.46.0 from its GitHub release, checked against the asset's SHA-256 digest. I skipped 2.47.0 and 2.48.0, which came out in the last two days.
- `runtimes/t3-0.1.4-nightly.20261028.3824-darwin-arm64` and `runtimes/t3-0.1.11-nightly.20261119.4928-darwin-arm64` come from their tags' releases, checked against each release's `SHA256SUMS`. The tarballs stay in `runtimes/dl-3824` and `runtimes/dl-4928`.
- `sandbox` is the main sandbox. Its server runs the 3824 runtime on port 47391, and its token is in `sandbox/session.token`.
- `sandbox-4928` runs the 4928 runtime on port 47392, with its token in `sandbox-4928/session.token`.
- I made each token by exchanging the pairing code from the server log at `POST /oauth/token`. Both answer `GET /api/auth/session` with `authenticated: true`. The sandboxes have no projects or threads yet.

Start them again after a reboot like this:

```
T3_BIN=~/CandyWrapper-research/runtimes/t3-0.1.4-nightly.20261028.3824-darwin-arm64/t3 scripts/sandbox-server
SANDBOX_DIR=~/CandyWrapper-research/sandbox-4928 SANDBOX_PORT=47392 \
  T3_BIN=~/CandyWrapper-research/runtimes/t3-0.1.11-nightly.20261119.4928-darwin-arm64/t3 \
  scripts/sandbox-server 0.1.11-nightly.20261119.4928
```

The research folder still lacks what the old Mac built up over time. `perf-home-pristine` is the frozen perf workload that `scripts/perf-review` compares against, and `scripts/perf-review --make-workload` rebuilds it once the sandbox has threads. `downloads/lucide-static-0.564.0` is what the icon generators read, and an agent can fetch it from npm. `sandbox-3824-ref/demo-repo` is a path that `SettingsScreensFidelityTests` shows. `backups/release-signing` has to come from the user.

## Only the user can supply

1. Install Xcode. The app target, `scripts/build-test-app` and the three XCTest files need it. Then run `sudo xcode-select -s /Applications/Xcode.app` and accept the license, both with sudo.
2. Copy `.git/info/secret-patterns` from the old Mac. Until then the pre-push hook refuses to run, so nothing can be pushed from here.
3. Copy `~/CandyWrapper-research/backups/release-signing` and put the Developer ID identity and the Sparkle key in this Mac's Keychain. Only needed to release from here (`docs/release.md`).
4. Decide whether agents get passwordless sudo here. `scripts/run-app` and the html-benchmark scripts run `sudo launchctl asuser`.
5. Say when the screen is free for agents. Every on-screen check in AGENTS.md takes the screen and drives the app.
