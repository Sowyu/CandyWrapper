# T3 Code Nightly: 2994 to 3105

Range: v0.0.46-nightly.20261011.2994 .. v0.0.46-nightly.20261014.3105. 187 commits. Most of it is server performance work on SQLite, mobile work and provider fixes. The wire changed very little: no new RPC, no change to `rpc.ts`, auth, pairing or the HTTP API, and the orchestration protocol stays at 2. Line numbers below are in the 3105 tree. "CW" is CandyWrapper at Packages/CandyKit/Sources unless a path starts with App/.

Theo's 2026-10-14 post ("Shipped a ton of perf improvements to the sqlite db ... If you saw 'reconnecting' banners, like, ever, that should now be resolved on nightly") covers these server commits: a74ce48f9 (#19205, stop fsyncing on every commit, so slow disks no longer drop clients), 8659fcf14 (#19226, thread list reads no longer freeze the server), 614b432a7 (#19304, durable checkpoints on macOS), 5fc1c5cb4 (#19324, checkpoints off the event loop), 4cd0076ec (#19305, cached statements no longer hold large parameters), fb8d0fc19 (#18471, planner statistics on open), 3b2ebcee2 (#18890, streamed events no longer rewrite the whole thread row), 8855a6dd0, bac35a2ff, 2d14185f3, fd9cdaed1, 173a97097 and 06a84de3b. A frozen event loop was the cause of the banners: the socket stopped answering pings and probes. They all ship inside the server binary, so a client gets them by running a 3105 server. Only one client-side change belongs to the same story, 5bba76443 (part 3).

## 1. Wire changes

### Breaks

None. A CW build pinned to 2861 works against a 3105 server (checked on a sandbox, part 5).

### Degrades

1. New thread event `thread.pull-request-link-updated` carrying one `ThreadPullRequestLink` (4d73e1d5c, packages/contracts/src/orchestrationV2.ts:1770, JSON :2595). PR sync now sends only the link that changed, where it used to send `thread.pull-request-synced` with the whole thread. CW's thread stream decodes it as `.unknownEvent` and advances the cursor (T3Protocol/Domain/ThreadStream.swift:166-186), so nothing breaks. CW reads thread PR links from the shell stream only (App/Sources/PullRequestsController.swift:917-925, ThreadSession.swift:347), and the server folds the event into the shell's `thread.pull-request-synced` (apps/server/src/orchestration-v2/ProjectionStore.ts). The detail view's `AppThread.raw.pullRequests` goes stale, but nothing in CW reads it.
2. `continueThreadsAfterServerUpdate` now defaults to true, and the server caps it at three automatic continuations in a row (b9ad3daf8, settings.ts:1129). CW's default was false (T3Protocol/Domain/Settings.swift:163), so the reset dot showed on a 3105 server's default value.
3. Antigravity `apiKey` and cliproxy `managementKey` are now secrets (d514a8c61, settings.ts:768, :824). The server stores them apart and sends `••••••` (apps/server/src/settingsSecrets.ts:22), and a write of that marker keeps the stored value. CW shows the marker in its password field and sends it back unchanged, which the server keeps. T3's field now reads "Stored separately on the host." and shows "Stored secret, enter a new value to replace" as its placeholder (apps/web/src/components/settings/SecretInput.tsx). CW still says "Stored in plain text." (Features/Settings/ProvidersSettingsView.swift:186).
4. Git file paths keep leading and trailing whitespace (aef0e9ca4, git.ts:14, :133, :236). CW sends paths as it got them (T3Protocol/Domain/Vcs.swift:318). No change needed.

### Keeps working (additive, CW ignores them)

5. `workspaceStrategy` on `thread.subagent-launch`-style commands and `isolation: shared|worktree` on the MCP `delegate_task` input (25629a76a, orchestrationV2.ts:3123, orchestratorMcp.ts:177).
6. `subagent` outcome on the internal `thread.background-work.settle` command (265fb7000, orchestrationV2.ts:3217). Server only.
7. `notAppliedVersion` on the desktop update state (eeaac49a9, ipc.ts:292). Electron only.
8. Default Claude text generation model is `claude-haiku-5-5` (8c027980e, model.ts:195). Server side.

### Server process and update contract

9. One database owner per T3 home (570542662, apps/server/src/serverOwnership.ts, server.ts:747). Before it opens the database, a server takes an exclusive SQLite lock on `<home>/userdata/server-owner.sqlite` and holds it for its lifetime. A second server on the same home exits with code 78 (`SERVER_EXIT_CODE_STATE_DIR_OWNED`, desktopBootstrap.ts:6) and the message "A T3 Code server already owns <dir>...". It also refuses when `server-runtime.json` names a live server from before the lock. `server-runtime.json` gained `ownerId`. The desktop app stops restarting a backend that exits 78, and the service launcher idles instead of crash looping (serviceLauncher.ts:790). CW's discovery decodes the runtime file with `ownerId` ignored (T3Client/LocalServer/LocalServerDiscovery.swift:7-16). CW had no idea of the lock, so a CW-started server could race a T3 server that was still migrating and had not yet written `server-runtime.json`.
10. Service updates (3417bc385, serviceLauncher.ts:42). The trial deadline went from 120 s to 30 minutes, because migrations and SQLite's optimize on a large database block the trial's main thread. The launcher refuses an update whose database backup won't fit on disk, with a reason that ends "The server was not stopped." Clients must wait longer than the deadline: `SERVER_UPDATE_RESUME_TIMEOUT` went from 4 to 32 minutes (packages/client-runtime/src/state/server.ts:132). CW waited 240 s (T3Protocol/Domain/ServerUpdate.swift:148), so a slow but healthy update on a large database showed as failed.
11. A pending service update fails with reason `state-dir-owned` when another server owns the home, without restoring the backup (serviceLauncher.ts `#idleWhileStateDirOwned`).

## 3. Client fixes in the range

1. Reconnect (5bba76443, packages/client-runtime/src/connection/supervisor.ts:39-50, 696-740). T3 counted the first config snapshot inside the 15 s setup budget, so a cold server with a large database dropped a working socket and showed "reconnecting". Now each route that reaches "synchronizing" gets 75 s more. CW's setup ends when the socket opens (T3Client/ConnectionSupervisor.swift:178-196, 320-337) and never waits for the snapshot, so it never had this failure. CW also sends no pings on direct routes, where T3's socket pings and drops after 15 s without a pong (rpc/protocol.ts:12), so a busy server never makes CW show the banner on its own.
2. T3 Connect (a143fa3c5, connection/errors.ts:48-62, relay/errorPresentation.ts:46-48). The relay's `managed_endpoint_allocation_not_ready` while a host swaps in a new tunnel is now transient and retried, with "The environment's T3 Connect tunnel is still being set up.". CW mapped every `RelayEnvironmentConnectNotAuthorizedError` to blocked (T3Client/Connect/RelayError.swift:83-88), so it stayed on "Connection failed" until a wake or a network change.
3. Relay 504 (e6626ee16, relay/errorPresentation.ts:71-89). A link that the relay cut off with an untyped 504 now says "Relay timed out before it finished the request (HTTP 504)...". CW said "Could not connect relay environment." (RelayError.swift:74).
4. Attachment images re-downloaded on every reconnect (1af138668). The server now derives an attachment id from the bytes too (apps/server/src/attachmentStore.ts `chatAttachmentStableKey`, ws.ts:405), so ids never change bytes, and mobile caches by id. CW already caches by attachment id on disk (App/Sources/ComposerController.swift `attachmentSource`, a864c45). Against a server older than 3105, editing a queued message's image can reuse the old id, and CW then shows the earlier image. The official mobile app has the same edge.
5. Large pasted images (adb04202b, after 3105 on main). A PNG or JPEG longer than 2000 px is scaled to 2000 px in its own format when attached, because Anthropic rejects such images once a request holds more than 20 images, and one large paste broke every later Claude request in the thread (packages/client-runtime/src/imageAttachmentSize.ts, apps/web/src/lib/imageCompression.ts). CW passed images under the byte limit through untouched and capped re-encodes at 2048 px (Features/Composer/ComposerAttachments.swift:234-311).
6. Context meter "1000k" (58d253231). CW had the same boundary (Features/Thread/ThreadContextWindowMeterView.swift:55).
7. Desktop backend readiness (DesktopBackendManager.ts:615-636). T3's desktop app never kills a backend for starting slowly. It probes in rounds while the child lives. CW stopped its own server after 60 s without a descriptor (T3Client/LocalServer/LocalServerLauncher.swift:25, 262-274), which on a large database could kill a server mid-migration and loop.

## 4. CW's own runtime and update flow against the new rules

1. The runtime CW installs and its update button target `ServerVersionSkewLogic.clientVersion` (Features/Settings/ServerVersionSkewLogic.swift:8-14, App/Sources/ServerController.swift:300, ServerUpdates.swift:251). That was still 2861, so a fresh install and the update button got 2861, without the SQLite fixes, even though the app runs fine on 2994 and 3105. Re-pinning moves it.
2. CW never starts a second server where it can see one (`LocalServerDiscovery.discover`), but it could not see a server that holds the owner lock before it writes `server-runtime.json`. And an owner-refused start (exit 78) showed "The T3 server exited during startup (status 78)."
3. CW's own-runtime update installs, activates, stops and starts. Nothing went back to the previous runtime when the new one failed to start, and nothing protected the database from a trial that migrated it and then died.
