# M10 abuse and failure stress test, 2026-10-12

Task `abuse`: the live app under abuse and network or server failure while turns stream. Zero crashes are tolerated.

## Setup

- My own T3 server: a copy of `sandbox/t3home` in `../CandyWrapper-research/abuse/t3home`, the installed runtime (`0.0.46-nightly.20261009.2861`) started like `scripts/sandbox-server` (env -i, own `--base-dir`, port 47491, detached).
- The app got its own bearer session (`t3 auth session issue --label abuse-app`), so revoking it left the test tools working.
- A fault proxy between app and server (`/tmp/cw-abuse/proxy.swift`, listen 47490, control port 47493). Commands: `stall`/`resume`, `drop` (shut both sockets), `slow <ms>` per server chunk, `refuse on|off`, and one-shot damage of the next server text frame: `corrupt` (bad JSON), `truncate` (half the JSON), `dup` (frame sent twice), `garbage` (a frame header claiming 65 KB followed by 15 bytes, then a FIN to the client while the proxy keeps reading it), `halfclose` (FIN at a frame boundary). It hides the client's permessage-deflate offer so frames are plain JSON; with compression on, `corrupt` only broke the inflater.
- Debug build `dev.candywrapper.test.abuse`, `--server http://127.0.0.1:47490`, its own thread cache (`CANDY_THREAD_CACHE=/tmp/cw-abuse/cache`).
- Turns came from `scripts/perf/turn.swift` straight to the server (the app only watched), prompt "write a 600-word story about a lighthouse keeper who collects lost keys" on claude-haiku-5-5. Claude sends the answer as one final item, so "mid-stream" means mid-run: thinking rows and the Working timer were live, the text landed at 9 to 21 s.

Measurements:

- Hangs: `/tmp/cw-abuse/hangwatch.swift` asks the app for an accessibility attribute every 50 ms (answered on the main thread) and logs replies slower than 100 ms, starting a `sample` when one is still running. `sample` attaches too late for short hangs, so the stacks below come from `xctrace` Time Profiler recordings of the same runs, cut to the hang window (`/tmp/cw-abuse/tpwin.py`).
- Memory and CPU: `scripts/perf/probe.swift rusage` before and after; settle CPU over 10 to 20 s with the hang watcher paused.
- Correctness: after each scenario the thread was opened again, left to settle, and the app's cached projection (written from its store when no run is active, like T3's `shouldPersistThread`) was compared with the server's bounded snapshot read back over HTTP (`/tmp/cw-abuse/verify.py`): messages, runs, runtime requests and visible turn items by id, order and content.
- Motion: ScreenCaptureKit window recording at 30 fps, then a one-frame-flash scan (`/tmp/cw-abuse/flicker.swift`: a frame that differs from both neighbours while they match each other).

## Bugs found and fixed

### 1. A socket that dies mid-frame wedged the connection for good

F7: the peer sent a frame header and part of its payload, then a FIN, and kept reading. `URLSessionWebSocketTask.receive()` never returns in that state (a FIN at a frame boundary is reported fine), and the delegate gets no completion either, so the app sat in CLOSE_WAIT. With no idle keepalive (a deliberate choice, see `ConnectionSupervisor`), nothing noticed: the sidebar kept a finished run "Working", and an unanswered call kept "Some requests are slow" on screen. Only an app activation probe recovered it. T3's Effect client pings every 5 s and drops a socket whose Pong misses the next tick (effect-smol RpcClient.ts:1205-1227), so T3 recovers within 10 s.

Fix (`T3Client/RPCConnection.swift`): a watchdog that runs only while a reply is owed, meaning a unary call is in flight or a stream has had neither a chunk nor its exit. After 5 s without any inbound frame it sends a Ping; a Pong missing after another 5 s closes the socket with `pingTimedOut` and the supervisor reconnects. A successful Pong marks quiet subscriptions answered, so a terminal or status stream that never sends costs one Ping and nothing more. With nothing owed no task exists, and idle stays at 0.3 wakeups/s. Tests: `RPCConnectionTests.aSilentSocketWithACallOwedIsClosed`, `aSlowCallOnALiveSocketKeepsItOpenAndTheWatchdogEnds`, `aQuietSubscriptionNeedsOnePongThenNothing`. On screen, F8 recovered by itself.

Left: a mid-frame EOF while nothing is owed (no call, no new stream) still waits for the next call, app activation, wake or path change. Only a per-socket keepalive covers that, which the supervisor avoids for battery.

### 2. Every ⌘K and dialog stalled the main thread 120 to 255 ms

Hang watcher: three hangs of 215, 122 and 190 ms during ⌘K/Esc ×3. The stacks showed `ModalHost.blurredSnapshot` building a new `CIContext` per open, which sets up a Metal context and loads Core Image's binary archives (about 70 ms of the 90 ms per open in the Debug build). Every `ModalHost` dialog took the same path.

Fix (`DesignSystem/Components/ModalHost.swift`): the backdrop blur runs on the CPU with `vImageConvolve_ARGB8888`, a 7x7 Gaussian kernel (sigma 1, edges extended) over the quarter-size bitmap, well under 1 ms and no GPU context. It blurs the sRGB-encoded values as Chromium does for CSS filters; Core Image blurred in linear light, up to 31 levels away at sharp edges. Test `OverlaysFidelityTests.vImageBlurMatchesCoreImage`: within 2 levels of Core Image's Gaussian in gamma space. The dialog fidelity cases are unchanged (3.65%, 2.94%, 0.63%). After the fix the same ⌘K/Esc ×3 had no hang over 100 ms.

### 3. A keyboard jump kept a stale multi-selection

After the switching storm a thread stayed highlighted as selected while another was open. `thread.jump.N` and `thread.previous`/`next` opened the thread without T3's `navigateToThread`, which clears the selection and moves the Shift-click anchor (Sidebar.tsx:3144-3158, used by the key handler at 4881-4889). Fix: `SidebarContentView.navigated(to:)`, called from the shortcut in `App/Sources/ThreadSession.swift`; test in `SidebarLeftoverTests.toggleAndRangeSelectFollowListOrder`. How the row got selected during the storm is not certain; a click that picked up another agent's ⌘ is the likely source.

## Left as they are

- First open of a thread right after launch, in the Debug build: 170 to 200 ms on the main thread (`ThreadViewModel.derive` 59 ms, `TimelineView.setItems` 43 ms, `ThreadController.open` 61 ms in the 450 ms window around the hang). Warm switches stayed under 100 ms through three rounds. Needs a Release measurement before anything changes; I didn't build Release because the disk was nearly full.
- One 1.3 s hang during the second switching round of a fresh app, seen once and not reproduced in two traced runs; the late `sample` showed the main thread idle with `HoverSync` calling `windowNumberAtPoint` (a WindowServer round trip) while four agents recorded and drove the screen.
- Live resize: a probe waits up to 113 ms while resize layouts run back to back (`MainWindow.layoutIfNeeded` 106 of 236 samples, `TimelineView.layout` 22). Frames keep coming; it is continuous work, not a stall.
- Peak footprint during the switching storm reached 133 MB after the fixes (199 MB before the blur fix, when every ⌘K built a Metal context); it settles at 71 to 75 MB.
- `t3 auth session revoke` from the CLI doesn't close sockets that are already open; that is the server's behavior.

## Side effects

- `/tmp/cw-ui/type` checks that my app is frontmost only once, before it types. Twice another agent's app (pid 93491, `/tmp/cw-dd-load`, server 47411) came to the front during my typing, so part of a message ("300-word story about a sea otter." and a Return) and the tail of another (" word three." and a Return) went to that app. A per-character frontmost check in `scripts/ui/type.swift` would stop this.
- My frame recordings filled the shared disk once (ENOSPC for a few minutes); I deleted them.
- Incremental app builds in `/tmp/cw-dd-abuse` began failing in the `Trim Sparkle` phase ("bundle format unrecognized"): the log shows the framework copy finishing after the trim script started. Deleting the built `.app` and building again succeeded. This is in project.yml, not in my change.
- About 18 real haiku turns in total, more than the 15 planned, because the queue spam created steers and queued runs.
