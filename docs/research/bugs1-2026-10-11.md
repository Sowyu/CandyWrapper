# Bug sweep, 2026-10-11

Worktree: `astra-bugs1`, baseline `ed8cce6`. No commit, delegation, T3 MCP calls or live-server changes.

## Sidebar reuse

Baseline `SidebarListView.swift:237-243` hid and pooled rows without clearing interaction state. `SidebarRowViews.swift:293` rebound the model without clearing it either. The row and child buttons kept hover/press state even when AppKit sent no exit event. T3 derives row colors from current CSS hover and keys rows by thread (`apps/web/src/components/Sidebar.tsx:1582-1593,5270`).

`SidebarRowBase.prepareForReuse` now clears pointer, press, keyboard and drag state, including child controls; the pool calls it before hiding, and rebinding another item calls it too. Same-item refreshes keep current hover. `SidebarListTests.recycledRowsForgetPointerState` failed before the fix with hover and active still true after scrolling 500 rows. It now passes. `SidebarReuseFidelityTests` compares recycled card/slim rows with fresh rest rows in both themes: four cases, 0% difference. This restores existing visual states, so no new CSS spec is needed. Scrolled the sandbox sidebar down and back on screen and moved the pointer away: no stale hover fill.

## Terminal lifetime

Baseline `AppleTerminalView.swift:2525` scheduled the bound `updateDisplay` method, retaining the view and its buffer until the next frame. The immediate weak-reference test failed for both `InputTerminalView` and `Terminal`; allowing 100 ms made it pass even before the fix. The redraw now captures weakly. `TerminalController.swift:56-62,517-520,535-541` also drops task handles after cancellation and weakens the focus host and stream attachment captures, so an outstanding subscription cannot own the closed pane. T3 disposes the terminal and its setup resources on teardown (`apps/web/src/components/ThreadTerminalDrawer.tsx:971-993`).

This was **not a reproduced permanent terminal leak**. Baseline heap counts already reached zero after a frame. Measurements on our own isolated app, using `/tmp/cw-perf/bin/probe rusage`, `heap`, and `leaks`:

- Baseline PID 84894: first terminal open 65,700,848 bytes footprint; hidden 64,439,280 bytes. Heap: one surface/view while open, zero after hide.
- Fixed PID 88868: three empty splits 65,455,088 bytes; 10,000 lines printed in one pane 72,680,432 bytes. Closed every terminal through its confirmation dialog. Final footprint 96,846,880 bytes, but heap contains **zero** terminal surfaces, input views or controller attachments. Only the static tuple key-path metadata remains. Dialogs raised peak footprint to 241,697,872 bytes, so total footprint is not proof of terminal retention.
- `leaks` reports 414 allocations / 19,840 bytes, rooted in macOS `com.apple.linkd.autoShortcut` NSXPC connections, not terminal objects. Baseline had 410 / 19,696 bytes of the same kind. No terminal leak was reported.

`TerminalLifetimeTests` now requires immediate release even with a pending redraw and a populated buffer, and passes without sleeping. Remaining: broader allocator/rendering-cache profiling if the total-footprint plateau still blocks the M7 demo. No forced cache flush, timer or polling was added.

## SnapShot files after send

Baseline `ComposerController.swift:1097,1231` dropped draft attachments before sending, while the success branches never deleted captures; only explicit image removal (`:2510`) did. Success paths now call `sentSnapShots` for new-thread, existing-thread/queue/steer, and fully successful fanout sends (`:1139,1191,1267,2190`). The helper deletes only files marked with SnapShot source metadata and removes their local preview mapping, letting sent previews use the server. Failed fanout sends restore attachments instead of abandoning their files. Failed single sends keep the existing restoration behavior.

T3's `apps/web/src/components/desktop/SnapShotCoordinator.tsx:166-193` first persists independent image data, then acknowledges the desktop capture. CandyWrapper needs its capture file to recover a pending draft, so it deletes after the server accepts the message instead. `SnapShotPendingCapture.removeDeliveredFiles` has a file-system regression: the old no-cleanup behavior leaves the capture behind; the fixed helper deletes it, preserves an ordinary user image, and tolerates repeat cleanup.

Screen check: the own bundle's permissions were already allowed. Setup test, enable, record Cmd-Option-S, capture own window. An existing-thread send (`Reply OK.`) removed a 482,307-byte file. A new-thread send (`Reply OK for SnapShot cleanup test.`) removed a 1,937,723-byte file. Both used Claude Haiku 5.5. The new thread became `Acknowledge Snapshot Cleanup Test`, returned OK, and displayed its sent attachment. The isolated SnapShots directory is empty. No macOS permission dialog appeared.

The coordinator row stays partial: pre-delivery crash queue, in-flight-send recovery, and stash/source synchronization remain outside this fix. Partial fanout retry was checked in code, not on screen.

## Server integration isolation

The historical failure is recorded in `docs/research/wp710b-thread-leftovers-2026-10-11.md:42`: a shared `sandbox-localserver` home made one worktree discover another's server. Baseline already includes `ff6ecf6`, which replaced it with a package-local, per-process home. The original integration test passed before this sweep; it would be misleading to claim a new reproduction on this baseline. The official discovery intentionally reuses a live runtime file (`apps/server/src/cli/pair.ts:260-287`). Production discovery must keep doing that.

The test home now has a UUID rather than a recyclable PID (`LocalServerIntegrationTests.swift:12-15`). `otherRunningServerDoesNotBecomeOurs` (`:33`) starts a decoy under another home, starts our lifecycle while it remains alive, verifies different process/environment identities, shuts ours down, verifies the decoy remains discoverable, and stops only that decoy. The original authenticate/connect/priority/stop/restart assertions remain intact. No product discovery behavior changed.
