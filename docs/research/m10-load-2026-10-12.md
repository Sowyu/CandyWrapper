# M10 load and endurance stress test, 2026-10-12

Task `load`: does CandyWrapper stay fast, light and correct with far more data than anyone has, and over hours? Six fixes came out of it. The numbers below are Release builds (`dev.candywrapper.test.load`, ad hoc signed).

## Setup

Data, all under `../CandyWrapper-research/`:

- `load-home-a` to `load-home-e` are copies of `sbs-home-seed` (docs/benchmarks.md, "Milestone 8 side by side", "Data"), each with a fresh `userdata/environment-id` so the app sees five environments.
- Home A got four more projects (`atlas`, `borealis`, `cobalt`, `dynamo`, git repos in `sandbox/load-projects/`, created through `POST /api/projects/mutate`) and legacy v1 rows that T3's own `LegacyV1ThreadImporter` imported on the next start: 1,000 small threads (200 per project, 2 to 8 messages, titles like "update deps romeo 200"), threads of 2,000, 3,500 and 5,000 messages, an assistant reply with an 18,000 line Swift block (1.1 MB) and one with 800 paragraphs (315 KB). The log read `importedThreadCount: 1005`; the transcripts hydrated on the first read (`importedMessageCount: 13430`).
- Homes B and C got 150 small threads and the two huge replies each; D and E stayed at the seed's 50.
- Two real full-access turns in home A made a Bash item running `seq 1 600000` and a diff of 17,500 lines (`big.txt` 3,000 lines replaced by 4,000, 30 files of 200 lines replaced by 150). Claude's Bash tool returns at most about 150 KB even with `BASH_MAX_OUTPUT_LENGTH` set, so I widened that item's stored output to the full 4.1 MB in the projection table with the server stopped (`/tmp/cw-load/bigtool.py`).
- At the end the five servers held 1,063, 207, 207, 52 and 51 threads: 1,580 in the sidebar, of which about 1,400 sit in the Settled shelf.

Servers: the installed runtime (`0.0.46-nightly.20261009.2861`), started like `scripts/sandbox-server` (env -i, own `--base-dir`, detached) on ports 47411 to 47415. The app got all five as `--server` pairs (the first is the primary) plus `--fake-t3-connect`. The shared sandbox on 47391 and `~/.t3` were not touched.

Tools, in `/tmp/cw-load/` (not committed):

- `frames.swift`: the ScreenCaptureKit method from docs/benchmarks.md, with HID pixel scroll events every 8 ms, plus the gap sequence and a check that the app stayed frontmost.
- `spindump -onlyTarget` (1 ms) for main thread profiles; `-timeline` to read single keystrokes and hangs in order. `sample` showed an idle main thread even when the app was busy for seconds on this machine, so no numbers here come from it.
- Hangs: an AX-polling watcher like the abuse task's gave false positives here (accessibility and TCC round trips took up to 1.2 s with an idle main thread), so I counted hangs with a temporary run loop observer in the app (`CANDY_LAUNCH_TIMING`, removed again): any main run loop pass busy for over 100 ms printed `HANG <ms>`.
- `procstat` (CPU, wakeups, footprint), `proc_pid_rusage` for footprint and lifetime peak, `powermetrics` for Energy Impact.
- `scripts/perf/turn.swift` with a `TURN_RUNTIME` and `TURN_PROJECT` option drove turns. 21 real claude-haiku-5-5 turns in the load part (one of them by accident, see Glitches), 14 in the endurance run.

The machine was shared with four other agents, their apps and builds; load averages ran 3 to 16 and `/tmp` filled up once. Frame gap percentages swing with that load, so the fixes below are judged by main thread time per operation, which is stable.

1. T3's first-run decision reads only whether there is more than one project or thread and the first of each (onboarding/firstRun.logic.ts:90, :94, :108). The loop now stops after two of each. `App/Sources/WelcomeOnboardingController.swift`.
2. The answer is cached per screen point and cleared by pointer moves, window key, move, resize and occlusion changes, app activation and native menus; it also expires after 0.25 s so another app's window sliding over a still pointer still takes the hover (marked `ponytail:`). `DesignSystem/Base/HoverSync.swift`.

6. `SidebarModel.sortSettledThreads` and `sortActiveThreadsByOrderKey` (threadSort.ts:56-69, :342-371) sort small keys and reorder once, same stable order, one shared `Locale`. `ThreadRelationships.related` hands the Lineage card only the shells that can carry an edge to the open thread (itself, parent, children, the projection's subagent and transfer threads, the merge target); `immediate` only reads those (RT/threadRelationships.ts:162-182). New test `relatedShellsGiveTheSameLineage`. `T3Store/SidebarModel.swift`, `T3Store/ThreadRelationships.swift`, `Features/Thread/ThreadLineageController.swift`.

## Endurance

The endurance app was a copy of the Release build from 09:39 (fixes 1 to 5 in, fix 6 not yet), with its own bundle id (`dev.candywrapper.test.loadendure`), against the same five servers and the fake T3 Connect, for 135 minutes (09:40 to 11:56). `/tmp/cw-load/endure.py` sent a claude-haiku-5-5 turn ("Reply with the single word ok") every ten minutes into its own thread, pressed a sidebar row through Accessibility every two minutes (no focus change), ran `procstat 60` every minute and `powermetrics` at one-minute samples. Until 10:22 the turn thread sat below the visible sidebar, so its turns arrived in the background; then I pinned it (`thread.pin`) and from 10:30 every turn ran with the thread open. My load tests ran against the same servers until 10:30, so the first hour includes their shell traffic.

- No growth that doesn't settle. Footprint fell from a median of about 100 MB in the first hour (my load tests' threads and turns) to 73 to 79 MB in the second, lifetime peak 167 MB. CPU stayed at 0.14 to 0.31% per window with a turn every ten minutes and a thread switch every two; 22 s of CPU in 135 minutes.
- Energy Impact is about 0 in quiet minutes (0.01 to 0.1) and 4 to 49 in minutes with a turn, a switch to a 2,000 or 3,500 message thread, or the load tests' traffic.
- Package idle wakeups stepped from about 0.02 to 0.3 per second at minute 49 and stayed. Interrupt wakeups, which count every wake, stayed at 0.6 to 0.8 the whole run, and the load test app showed the same step at the same time. The machine's load average fell from 8 to 16 to under 2 then, so the same wakes started landing on an idle package; the app did not wake more often.
- All 14 turns completed. 12 main thread passes over 100 ms, all on thread switches: 111 to 215 ms opening the 2,000 and 3,500 message threads and the 315 KB markdown reply, once 687 ms for that reply while the machine was loaded (it takes 0.31 s to its first frame on an idle machine, 0.15 s of it TextKit laying out 800 paragraphs).
- No crash, no reconnect.

Idle with no turns, measured after the run with the final build: one environment 0.00% CPU, 0.02 pkg idle and 0.08 interrupt wakeups/s, 35 MB; five environments and 1,580 threads 0.07%, 0.05 and 0.13, 58 MB. The app that had run all the load tests for two hours sat at 0.06 to 0.07% with 0.40 interrupt wakeups/s: its sidebar showed many threads touched in the last hour, each relative time label ticks once a minute on its own phase, and each tick rebuilds the whole list (about 20 ms with 1,580 threads). That stays under the 1 per second target and fades as the threads age; see Left.

## Follow-up 2026-10-13: lazy code block layout

`MarkdownTextBox` now lays out a box of 200 or more paragraphs one paragraph at a time, when something draws, hits or measures it. The box still needs its height up front, so a scan counts lines: in a fixed pitch font, printable ASCII and tabs are as wide as their columns, so a paragraph narrower than the box is one line without laying it out. Only paragraphs that may wrap, or hold other characters, lay out at open. Selection, find highlights and the find foreground now touch only the lines near the dirty rect, through a binary search over the paragraphs. `codeBlock` also sets the paragraph style before the token colors split the string into runs; added after, it rebuilt every run's attributes, 0.1 s here. T3 renders the whole block as Shiki HTML with no size limit (ChatMarkdown.tsx), so the block keeps its full height and every line. Tests `lazyTextBoxMatchesFullLayout` (same breaks, spans, widths and hits as the full layout, wrapped and not, with tabs, trailing spaces, long and non-ASCII lines) and `lazyTextBoxLaysOutLinesFarBelowTheFold`.

Measured the same way as fix 5, Release builds, but with home A alone on 47411, opening "Huge code reply" through ⌘K (`CANDY_THREAD_TIMING`, `proc_pid_rusage`, `spindump -onlyTarget` for main thread CPU):

## Sidebar updates, 2026-10-13

Task `sidebar`: the list rebuilt every row model, re-sorted every shelf and diffed all 1,582 items on each shell change and each relative time tick.

`SidebarListCache` (`Features/Sidebar/SidebarListCache.swift`) now keeps each thread's derived values, each shelf's order and each row model between builds. A thread whose shell is unchanged keeps its values. A shelf re-sorts only when a thread enters it, leaves it or changes its sort key; a thread that changes in place takes its old slot. A row model rebuilds only when its thread, its selection state or one of its clock-driven fields changes; each row knows when its time label, snooze label, Woke state or snooze permission next changes. When nothing moved, the sidebar patches the list it already shows (`SidebarListView.patchItems`) and reconfigures only those rows on screen. The app's merge tells the sidebar which threads it re-scoped (`MergedShell.lastChangedThreadIds`), so it compares only those shells. `SidebarLoadTests` checks that a one-thread change builds one row model, that the content view patches instead of rebuilding, and that the cached list equals a fresh build after a settle, unsettle, snooze, pin, reorder, delete, selection, clock steps, a snooze ending, a collapse and a scope change.

Measured with `CANDY_SIDEBAR_TIMING=1` (new, passed through `scripts/run-app`; `nocache` builds from scratch every time), a Release build against the five load homes, the whole settled shelf shown (1,582 items), the machine shared with other agents and a browser build:

| Update | Before (`nocache`) | After |
|---|---|---|
| One thread renamed (`thread.metadata.update`, 10 times) | 9.5 to 14.4 ms, median 10 | 0.6 to 2.0 ms, 1 row model built |
| Relative time tick | 22 to 30 ms | 0.25 to 1.1 ms, 1 or 2 row models built |
| "Show 25 more" near the end of the list | 10 to 19 ms | 7 to 12 ms, 25 row models built |

The before column ran the same build with the cache off, so it already had the list's in-place item replace; the original code was a little slower still. On an idle machine the synthetic 1,580-thread list in `SidebarLoadTests` went from 7.0 ms per change and 6.9 ms per tick to under 1 ms. What's left per change is the one row view's configure (about 0.4 ms) and hashing the hinted ids. A change that moves a thread to another shelf, a list state change (selection, expanding a shelf) and the Working beta shelf still assemble and diff the whole list, from the cached rows; with rows coming in or going, the list's diff and their motion dominate, as the Show more row shows.
