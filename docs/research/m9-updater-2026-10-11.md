### A2. Update machine and desktop service

State is one record (packages/contracts/src/ipc.ts:270-287; initial values apps/desktop/src/updates/updateMachine.ts:18-41). Status values: `disabled | idle | checking | up-to-date | available | downloading | downloaded | error` (ipc.ts:71-80).

Transitions (updateMachine.ts):

| Event | Result | Lines |
| --- | --- | --- |
| Check start | `checking`, `checkedAt` set, message cleared; notes kept only if something is already downloaded, `downloadPercent` 100 in that case | 43-59 |
| Check failure | If a download exists: back to `downloaded`, no message, `canRetry` true. Else `error`, message, `errorContext` "check" | 61-87 |
| Update available | `downloaded` if that version is already downloaded, else `available`; sets `availableVersion`, notes and `omittedReleaseCount` | 89-111 |
| No update | If a download exists: `downloaded`. Else `up-to-date` and clears versions and notes | 113-143 |
| Download start | `downloading`, percent 0 | 145-156 |
| Download progress | `downloading`, percent | 172-184 |
| Download complete | `downloaded`, both versions set, percent 100 | 186-200 |
| Download failure | `available` if a version is known (retryable) else `error`; `errorContext` "download" | 158-170 |
| Install failure | `downloaded` with message and `errorContext` "install" | 202-213 |

Service (`DesktopUpdates.ts`):

- Startup check after 15 seconds (`AUTO_UPDATE_STARTUP_DELAY`, :50, poller :705-718). Then a check every 4 minutes forever (`AUTO_UPDATE_POLL_INTERVAL`, :51, poller :719-733). No other trigger besides manual (pill, Settings button, menu) and a channel change.
- `autoDownload` and `autoInstallOnAppQuit` are both off (:933-934). Nothing downloads until the user clicks.
- A check is skipped while downloading or while another action holds the lock (:419-428). Only one of check, download, install, channel runs at a time (`tryStartUpdateAction`, :369).
- Progress broadcasts only on each 10 percent step, or at 100 (:230-246).
- Disabled reasons (:258-273): no feed config, dev or unpackaged build, env `T3CODE_DISABLE_AUTO_UPDATE`, Linux without AppImage or deb. Disabled state is `enabled: false, status: "disabled"` (:222).
- A found update whose version does not belong to the selected track is treated as "no update" (:743-754).
- Install: first sets `quitting`, writes a restart marker file for the backend, stops every backend with a 5 s timeout, then `autoUpdater.quitAndInstall(isSilent: true, isForceRunAfter: true)` (:628-650). If it throws, `recoverFailedInstall` restarts the backends and sets the install error (:551-583). Install is refused unless a download exists and no other action is running; it can wait up to 90 s for a running check (:52, 590-625).
- Download needs status `available` (:463).

Track (updateChannels.ts:1-18, DesktopUpdates.ts:390-404, 966-1013):

- Two values: `latest` ("Stable" in the UI) and `nightly`.
- A version matching `^[^-+]+-nightly\.\d{8}\.\d+$` is nightly, anything else is stable (updateChannels.ts:3, 16-18).
- Nightly turns on `allowPrerelease`, `allowDowngrade` and `fullChangelog` (DesktopUpdates.ts:394-398). Stable turns all three off.
- Changing track persists the setting, rebuilds the base state, applies the track, allows downgrade for that one check, then runs a check (:971-1013). It is refused while another action runs (`DesktopUpdateActionInProgressError`, :80-88).
- The default track comes from the running version: a nightly build starts on nightly (updateChannels.ts:16-18). CandyWrapper has no nightly-suffixed version scheme yet, so the default must be a user decision.

### A5. Remote update

`DesktopRemoteUpdates.ts` and `remoteUpdateFlow.ts` let a T3 server ask the desktop app to update itself. The desktop listens for requests on its telemetry control channel (`DesktopTelemetryPublisher`, :75-76), runs check, download and install steps through the same `DesktopUpdates` service (flow capped at 2 checks and 3 downloads, remoteUpdateFlow.ts:28-35), holds a prepared download for 5 minutes (DesktopRemoteUpdates.ts:29), and reports status back (`publishUpdateReport`). It only runs inside the Electron desktop shell.

A client that only connects to servers needs none of it. CandyWrapper does not send telemetry reports or accept control-channel requests, so skip it. If the user wants "update this Mac from the server UI" later, it is a separate feature.

## Sparkle mapping

### B1. Version, integration, size

- Latest stable is 2.10.0, published 2026-09-13 (api.github.com/repos/sparkle-project/Sparkle/releases/latest). It needs macOS 12 or later. CocoaPods is dropped (CHANGELOG, 2.10.0).
- Swift Package Manager works. Docs: "Enter `https://github.com/sparkle-project/Sparkle` as the package repository URL" and "The default options will let Xcode automatically update versions of Sparkle 2." (sparkle-project.org/documentation/). The package is one binary target pointing at `Sparkle-for-Swift-Package-Manager.zip` (10.2 MB download) with a pinned checksum (Package.swift on the 2.x branch).
- I downloaded and unpacked that zip: the universal (arm64 + x86_64) `Sparkle.framework` is 2.9 MB on disk. Inside: the binary 0.96 MB, `Autoupdate` 0.69 MB, `Updater.app` 0.34 MB, `XPCServices` 0.41 MB, localization resources 0.36 MB, headers 0.2 MB. An arm64-only, stripped bundle with headers and the XPC services removed should add roughly 1.5 to 2 MB. That is an estimate; I did not build it.
- The bundle can drop `Headers`, `PrivateHeaders` and, for a non-sandboxed app, `XPCServices` (see B8).

### B2. User driver callbacks mapped to T3 states

`SPUUpdater(hostBundle:applicationBundle:userDriver:delegate:)` takes any `SPUUserDriver` (SPUUpdater.h:62). Callbacks are from `SPUUserDriver.h` on the 2.x branch.

The natural fit is the Sparkle flow itself: found update, reply `.install` (that starts the download), extract, ready to install, reply `.install` (that quits and relaunches). T3's two clicks (Download, then Restart) map onto those two replies. The driver keeps the reply blocks and calls them from the pill actions.

Things T3 does that Sparkle does not give directly:

- `releaseNotes` as bullet groups. We have to build them from `itemDescription` or from the GitHub release body. Sparkle shows one release's notes, not "all releases newer than yours" the way electron-updater's `fullChangelog` does.
- A download that the user triggers is natural, but Sparkle skips versions only when the user replies `.skip`. T3 has no skip, so never reply `.skip`.
- Downgrade on track change. Sparkle offers only newer versions; `bestValidUpdateInAppcast:forUpdater:` (SPUUpdaterDelegate.h:234) can pick the item, but I did not confirm that Sparkle accepts one with a lower version. Treat nightly to stable downgrade as unsupported until tested.
- Persisted state across launch. Sparkle may resume with `state.stage == Downloaded` or `Installing` from a previous session, so the first `showUpdateFound` after launch can already be `downloaded`.

## Signing

### B3. Can Sparkle update an ad-hoc signed app

Short answer from reading the source (SUUpdateValidator.m on 2.x; I did not run an update): yes, if the EdDSA signature is valid. Ad-hoc to ad-hoc works because EdDSA alone is enough. Code signing is not required to match.

What Sparkle checks for an app-bundle update (`validateUpdateForHost:...`, SUUpdateValidator.m:296-311). The source comment reads:

> If the update is a bundle, then it must meet any one of:
> * old and new Ed(DSA) public keys are the same and valid (it allows change of Code Signing identity), or
> * old and new Code Signing identity are the same and valid

The code path agrees (:340-375):

1. The archive's EdDSA signature is checked against the old app's `SUPublicEDKey`.
2. If the old app is code signed, Sparkle also checks that the new app satisfies the old app's designated requirement (`codeSignatureIsValidAtBundleURL:andMatchesSignatureAtBundleURL:`).
3. `if (passedDSACheck || passedCodeSigning) return YES` (:373). Either one passes.

Facts that matter for ad-hoc:

- An ad-hoc app counts as code signed. `bundleAtURLIsCodeSigned` only returns NO for `errSecCSUnsigned` (SUCodeSigningVerifier.m:248-269). Its designated requirement is the `cdhash`, which changes every build. So step 2 fails for every ad-hoc update, and step 1 carries it. That is fine.
- Two guard rules still apply (SUUpdateValidator.m:271-292, 364-370). The new app must not drop code signing when the old one had it ("The old bundle is code signed but the update is not code signed."). A new app that is signed but corrupt is rejected even with a valid EdDSA signature.
- EdDSA keys cannot be removed once shipped ("Sparkle only supports rotation, but not removal of (Ed)DSA keys", :276).
- The Team ID check exists only as a key-rotation fallback, and only for Developer ID. In `codeSignatureIsValidAtDownloadURL:andMatchesDeveloperIDTeamFromOldBundleURL:` Sparkle builds `anchor apple generic and certificate 1[field.1.2.840.113635.100.6.2.6] and certificate leaf[field.1.2.840.113635.100.6.1.13] and certificate leaf[subject.OU] = "<team>"` (SUCodeSigningVerifier.m:363). It runs only when the EdDSA check of the archive fails and the app requires signed archives (SUUpdateValidator.m:76-93). `SUTeamIdentifierFromCode` returns nil "for ad-hoc or unsigned binaries" (SUCodeSigningVerifier.m:285).

The docs say the same in softer words (sparkle-project.org/documentation/, "Segue for security concerns"):

> Notarize and code sign the application via Apple's Developer ID program (if possible).
> Sign the published update archive (dmg, zip, etc), binary delta updates, and installer packages with Sparkle's EdDSA (ed25519) signature.

Self-signed certificate. Same rule: EdDSA passes alone. Bonus: a self-signed identity has a designated requirement tied to the certificate (not a cdhash), so step 2 also passes on every update signed with the same certificate, which gives a second check. No Team ID is involved. If the certificate changes, EdDSA still carries the update.

Developer ID. Both checks pass; the Team ID fallback becomes available for key rotation. Docs: "For regular application updates (not installer package updates), if you both code-sign your application with Apple's Developer ID program and include a public EdDSA key for signing your update archive, Sparkle allows rotating keys by issuing a new update that changes either your Apple code signing certificate or your EdDSA keys (but not both)."

Hardened runtime and library validation (this applies to us now: `project.yml:65` sets `ENABLE_HARDENED_RUNTIME: YES`, `CODE_SIGN_IDENTITY: "-"`, and there is no entitlements file). The docs say:

> If you enable Library Validation, which is part of the Hardened Runtime and required for notarization, you will also need to either sign your application with an Apple Development certificate for development (requires being in Apple's developer program), or disable library validation for Debug configurations only. Otherwise, the system may not let your application load Sparkle if you attempt to sign to run locally via an ad-hoc signature. This is not an issue for distribution when you sign your application with a Developer ID certificate.

So an ad-hoc or self-signed release with the hardened runtime very likely needs the entitlement `com.apple.security.cs.disable-library-validation` in the app, or the app will not load `Sparkle.framework`. Check this on the first real build. With a Developer ID build it is not needed.

Gatekeeper is a separate matter. Sparkle downloads with its own session, so updated files carry no quarantine flag set by a browser. The first install of a non-notarized app still needs "Open Anyway", as v0.1.0 notes say.

What the user must decide:

1. Stay ad-hoc (works with EdDSA only, Keychain re-prompts after each update because the cdhash changes), use a self-signed certificate on the build Mac (stable identity, no Apple account, still not notarized), or use Developer ID plus notarization (needs an Apple Developer account, removes "Open Anyway").
2. If ad-hoc or self-signed: accept adding the `disable-library-validation` entitlement.

### B5. EdDSA keys

- `bin/generate_keys` makes the key pair once. Docs: "It will generate a private key and save it in your login Keychain on your Mac." It prints the base64 public key for `SUPublicEDKey` in Info.plist and prints it again if run again.
- Export and import: "You can use the `-x private-key-file` and `-f private-key-file` options to export and import the keys respectively when transferring keys to another Mac."
- Back up the export outside the repo (a password manager or encrypted disk image). Keychain contents "will be erased if your keychain or system is erased". Losing the key breaks updates for every existing install; only a Developer ID signed app can recover through key rotation ("If your keys are lost however, you can still sign new updates for Developer ID signed applications through key rotation.").
- `bin/sign_update <archive>` prints `sparkle:edSignature="..." length="..."` for the enclosure. It reads the Keychain by default, or `--ed-key-file <path>` (`-` reads the key from stdin). It also signs an appcast XML in place and has `--verify`.
- `bin/generate_appcast <dir>` reads every archive in the folder, signs each with the Keychain key, writes `appcast.xml`, and makes deltas by default. Useful flags (main.swift): `--download-url-prefix`, `--channel`, `--full-release-notes-url`, `--embed-release-notes`, `--release-notes-url-prefix`, `--maximum-versions`, `-o`, `--ed-key-file`.
- Keeping the key out of the repo: leave it in the Keychain and call the tools with no key argument. Never pass `-s` (deprecated plain key on the command line). If a file is ever needed, keep it in `~/.config` or a temp dir and add the pattern to `.gitignore`. Docs: "Please ensure your signing keys are kept safe and cannot be stolen if your web server is compromised."
- Optional hardening: `SURequireSignedFeed` plus `SUVerifyUpdateBeforeExtraction` also sign the appcast (since 2.9). With a GitHub-hosted feed, this stops someone who gets write access to the repo's releases from pointing users at another download. It costs re-signing the appcast on every change. Worth it only if the user wants it.

## Hosting on GitHub Releases

### B4. Appcast URL

Confirmed problem. GitHub: "The latest release is the most recent non-prerelease, non-draft release, sorted by the created_at attribute." (docs.github.com/en/rest/releases/releases, "Get the latest release"). So `/releases/latest/download/appcast.xml` skips pre-releases.

I checked it live. Releases v0.1.0 and v0.1.1 are both `prerelease: true`, each with only the zip asset. `https://github.com/Sowyu/CandyWrapper/releases/latest/download/appcast.xml` returns HTTP 404 today. The plan's feed URL would break until a non-pre-release exists with `appcast.xml` attached.

Redirects. `/releases/latest/download/<file>` answers 302 to `/releases/download/<tag>/<file>`, which answers 302 again to the asset host, then 200 (I fetched a Sparkle release asset this way and got the 16 MB file). Sparkle reads feeds and archives with `NSURLSession`; I found no redirect handling code in its downloader (`Downloader/SPUDownloader.m` has none), so the system default of following redirects applies. Many apps ship GitHub-hosted feeds this way. I did not run Sparkle against this host. A manual test in the first build covers it.

Options:

1. Dedicated tag, recommended. Keep one release tagged `appcast` (it can be a pre-release), with a single asset `appcast.xml`. Feed URL: `https://github.com/Sowyu/CandyWrapper/releases/download/appcast/appcast.xml`. The URL is fixed, works while all version releases stay pre-releases, and `scripts/release` just replaces the asset through the API. Cost: one more release in the list, and deleting and re-uploading the asset on every release.
2. Raw file in the repo. `https://raw.githubusercontent.com/Sowyu/CandyWrapper/main/appcast.xml`. No extra release, but each release adds a commit, and raw.githubusercontent.com caches for about five minutes (from memory, not checked). The repo already has a rule to commit and push each batch, so this fits, but it puts a build artifact in history.
3. Stop marking releases as pre-release and use `/releases/latest/download/appcast.xml`. This matches the plan text. But "latest" then points at whichever stable release is newest, and that release must carry the full appcast, including nightly items. It also means every stable release has to attach a fresh `appcast.xml` or the feed goes stale. Nightly as pre-release works only if the stable release's appcast lists them.

Whichever is picked, build the appcast from a folder holding all archives you still want offered (`generate_appcast` is incremental over that folder), so older entries and the nightly/stable channel items stay together. Archive and release notes URLs use the version tag (`https://github.com/Sowyu/CandyWrapper/releases/download/v0.1.2/CandyWrapper-0.1.2-arm64.zip`), which works for pre-releases too. Use `--download-url-prefix` for that.

The feed URL goes into Info.plist as `SUFeedURL`. A delegate can override it (`feedURLStringForUpdater:`), but one fixed URL is simpler.

### B6. Scheduled checks

From the headers and source (SPUUpdater.h, SPUUpdaterSettings.m, SPUUpdaterTimer.m, SPUUpdater.m):

- `SUEnableAutomaticChecks` (Info.plist, bool): turns scheduled checks on. When it is set, Sparkle does not show the permission prompt ("This is not done if `SUEnableAutomaticChecks` is set in the Info.plist", SPUUpdater.h:236).
- `SUScheduledCheckInterval` (seconds): default 86400 (24 h, SPUUpdaterSettings.m:413). Minimum 3600 (1 hour): `minimumUpdateCheckInterval` returns `60 * 60` and the scheduler raises any smaller value to it (SPUUpdaterSettings.m:379-387, SPUUpdater.m:529-531). The 1-minute value applies to debug builds of Sparkle's own test app only.
- Timer: one `dispatch_source_t` timer on the main queue, wall-clock based, so sleep time counts (SPUUpdaterTimer.m:35-40). Leeway is 15 seconds (SPUUpdaterSettings.m:390-401). It is set for the time remaining until the next check, then re-armed after each check. If the last check is older than the interval at launch, Sparkle runs a check right away (SPUUpdater.m:557-560 area, "We're overdue! Run one now").
- Wakeups: one timer per interval, nothing polling. It fits the "nothing may run in the background" rule better than T3's 4-minute loop, which has no equivalent here. The cost of one check is one small HTTPS request.
- Differences from T3 to decide: T3 checks 15 s after launch and every 4 minutes. Sparkle cannot check more than once an hour. Options: call `checkForUpdatesInBackground()` once after `startUpdater` for a launch check ("it's recommended to only call this method immediately after starting the updater", SPUUpdater.h:120-122), and set the interval to 3600 or longer.
- `SUAutomaticallyUpdate` and `SUAllowsAutomaticUpdates`: leave automatic download off (`SUAllowsAutomaticUpdates` = NO). That matches T3's `autoDownload = false`.
- `lastUpdateCheckDate` and the skipped version live in the app's UserDefaults. Test builds with their own bundle id keep their own.

### B7. Channels

Docs (sparkle-project.org/documentation/publishing/, "Channels"): "By default, updaters only look for updates that are on the default channel." and "Updates are posted on the default channel unless specified otherwise." The delegate `allowedChannelsForUpdater:` returns the set of channel names (SPUUpdaterDelegate.h:113): "An empty set is the default behavior, which means the updater will only look for updates in the default channel. The default channel is always included in the allowed set." And: "Note that an updater cannot exclude itself from the default channel." Valid names use letters, numbers, dashes, underscores and periods. `generate_appcast --channel nightly` tags new items.

Mapping to T3's track:

| T3 | Sparkle |
| --- | --- |
| Stable (`latest`) | `allowedChannels = []`, finds only untagged items |
| Nightly | `allowedChannels = ["nightly"]`, finds untagged and `nightly` items, newest wins |
| Settings select change | store the choice, call `updater.checkForUpdates()` or `resetUpdateCycle()` |

Consequence: nightly users also receive stable releases, which is also true of T3 (its nightly track follows the highest version). Items must therefore be ordered by `sparkle:version` (the build number), not by track. The channel docs warn that channels "are not intended to be used for parallel releases". Nightly branches off and is superseded by a later default item, which fits.

### B8. Installation for a non-sandboxed, hardened-runtime app

- Docs: "If you do not sandbox your application and thus do not enable Sparkle's XPC Services, you may choose to remove these services in a post install script when copying the framework to your application." The two services are `Installer.xpc` (needed only for sandboxed apps) and `Downloader.xpc` (only for sandboxed apps without network access).
- Non-sandboxed apps use the framework's `Autoupdate` and `Updater.app` helper tools, launched directly. No `SUEnableInstallerLauncherService`, no mach-lookup exception, no network entitlement (those are in the sandboxing guide and only for sandboxed apps).
- Entitlements: none for Sparkle itself in a Developer ID build. For ad-hoc or self-signed with the hardened runtime, add `com.apple.security.cs.disable-library-validation` (see B3).
- Signing the bundle: Sparkle's helpers ship ad-hoc signed with the hardened runtime. Re-sign them inside-out when you sign the app: XPC services (if kept), `Autoupdate`, `Updater.app`, the framework, then the app. Do not use `--deep` blindly. The docs describe an exact order (sandboxing page, "Code Signing").
- Zip rule for the release archive: symlinks must be preserved ("macOS frameworks use symlinks, and their code signature will be broken if your archival tool follows symlinks"). `ditto -c -k --sequesterRsrc --keepParent` (what the v0.1.0 release used) keeps them.
- Install behavior: Sparkle extracts to a temp folder, quits the app, the helper swaps the bundle and relaunches. The app must be in a place the user can write, or Sparkle asks for authorization. `/Applications` owned by the user is fine.

### B9. Delta updates

Probably not worth it. The zip is about 11 MB (v0.1.1 asset is 11,636,939 bytes). Deltas save download size on a few MB per update, but each one adds files to sign, upload and keep per previous version, and Sparkle ignores one if the app on disk does not match its checksum. `generate_appcast` makes them by default, so turn them off with `--maximum-deltas 0`. Revisit if the app passes ~50 MB or users are on slow links. Ad-hoc re-signing can also change bytes inside the app between builds, which makes deltas less reliable.

## Open questions for the user

1. Code signing: ad-hoc (works, with the library-validation entitlement), a self-signed certificate on the build Mac (stable identity), or Developer ID with notarization (needs an Apple Developer account)?
2. Feed URL: dedicated `appcast` release tag (recommended), a raw file in the repo, or stop marking releases as pre-release so `/releases/latest/download/appcast.xml` works as in the plan? The plan's URL returns 404 today.
3. Check schedule: Sparkle cannot go below one hour. Is "one check at launch plus every 24 hours" acceptable (or hourly), instead of T3's startup plus 4 minutes?
4. Nightly versions: T3 detects a nightly by its version string. What should a CandyWrapper nightly be called, and which track does a fresh install start on?
5. Release notes popover: T3 shows it only on the nightly track. Do the same, or show notes for stable too? The notes need a source (the GitHub release body or text embedded in the appcast).
6. Switching nightly back to stable: T3 allows a downgrade for that check. Sparkle may not. Accept "stays until the next stable is newer"?
7. Sign the appcast too (`SURequireSignedFeed`)? It adds a re-sign step and protects against a compromised repo.
8. Should the pill's "Read more" and release links point at `Sowyu/CandyWrapper` (T3's point at pingdotgg/t3code, logic.ts:5-6)? I assume yes.
