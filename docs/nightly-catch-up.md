# Nightly catch-up

A scheduled T3 task runs this early on Monday and Thursday mornings in Melbourne, while the user sleeps, and any agent can run it by hand. The scheduler only knows the Mac's clock, which is on Paris time, so the task is set to 17:00 on Sundays and Wednesdays. That's 2am in Melbourne now, 3am from late October to late March and 1am from April to early October. The goal is that CandyWrapper matches the newest T3 Code Nightly, still works with the Nightly before it, and got no worse.

Nobody watches the scheduled run, so don't wait for answers. Put questions for the user under "Waiting on the user" in `PROGRESS.md` and carry on with whatever doesn't depend on them. Never publish a release.

## Steps

1. Run `scripts/preflight`. If it fails, stop and report why.
2. Work in your own worktree, because other agents may be editing the main checkout: `git -C /Users/mrm/CandyWrapper worktree add /tmp/cw-nightly-<date> origin/main`. Push from it with `git push origin HEAD:main`. Build and test there too, even when T3 started you in a worktree of its own: those live under `~/.t3/worktrees`, and `LocalServerIntegrationTests` refuses any server home under `~/.t3`, which stops the whole T3Client test process with a trap.
3. Find the newest Nightly with `git -C ~/CandyWrapper-research/t3code fetch -q --tags`, then `git -C ~/CandyWrapper-research/t3code tag -l 'v*-nightly.*' --sort=-v:refname | head -1`. The State section of `PROGRESS.md` names the Nightly the app last caught up with. If nothing is newer and no catch-up task is open, go to step 9.
4. Write `docs/research/nightly-diff-<build>.md` in the shape of `docs/research/nightly-diff-2994.md`. Wire changes come first, breaks before additions, then UI and behavior changes, each with T3's file:line and the CandyWrapper code it touches. To read the new tag's files, run `git -C ~/CandyWrapper-research/t3code worktree add /tmp/t3code-<build> <tag>`. Before porting, check that nothing slipped through: list every commit in the range that touches `apps/web/src`, `packages/client-runtime`, `packages/contracts` or `packages/shared`, tests and refactors aside, and check each one the notes don't cite by hash or PR number against CandyWrapper too. On 2026-10-22 the 3473 notes had missed 115 such commits and 33 gaps (section 6 of `nightly-diff-3473.md`).
5. Download `t3-<version>-darwin-arm64.tar.gz` and `SHA256SUMS` from the tag's GitHub release, check the checksum and unpack it into `~/CandyWrapper-research/runtimes/`. The scripts look there for any version the live T3 hasn't installed. Start a sandbox server for it on a free port with `SANDBOX_DIR`, `SANDBOX_PORT` and `T3_BIN`, as AGENTS.md shows for 2994. Leave the main sandbox server alone, since other agents use it.
6. Fix the wire first. The app must work with the new server and still with the previous Nightly, so test against both sandbox servers.
7. Then match every user-visible change exactly, in both themes, side by side with the official Nightly. `docs/research/m10-side-by-side-2026-10-12.md` describes the method. Start with what the user sees most: the thread, the composer and the sidebar, then settings and rarer panels. If it's more than one run can finish well, add what's left to `PROGRESS.md` as open tasks that point at the diff doc.
8. Once the wire work is done, re-pin. Set `T3_VERSION` to the new tag, check that tag out in `~/CandyWrapper-research/t3code` and update the State section of `PROGRESS.md`. Checking out the tag is the one change allowed in that clone. Also copy the new client bundle's `main-*.css` from `runtimes/<version>/client/assets` over `design/t3-source/main.css`, update its README, and regenerate the component references with `scripts/component-reference`. A fidelity test that fails afterwards marks a visual change to port. Until 2026-10-22 that stylesheet was still 2861's.
9. Audit the app on every run. Run the whole test suite, compare `scripts/perf-review` with the last saved run, and review everything this run changed for bugs, slow paths, leaks and security holes. Then, on screen against the sandbox and in both themes, open a thread, send one tiny turn, toggle the sidebar fast, and open settings and the command palette. Fix what broke, and list what you couldn't fix in `PROGRESS.md`.
10. Commit and push as each piece works, as AGENTS.md describes. Then clean up: quit your apps, stop the servers you started, give back the screen lock, and remove your worktrees and `/tmp/cw-dd-*` builds.
11. End with a report under 300 words: the Nightly you caught up to, what changed for the user, what's left, the test and performance results, and whether it's ready to release. The user replies "release" to ship it.
