# Revised fast-load benchmark on 3473 and pinned main

The revised matrix completed all three rounds on 2026-10-25, from **18:15:32.386 to 18:17:48.517 UTC**, without detected compiler/test overlap. All twelve runs synchronized, retained their content across reconnect, and recovered the complete synthetic history.

The shared-config revision removes the previously observed reconnect penalty in this comparison. It does **not** establish a cold-load speed win: combined shell-plus-thread readiness is **8.5% later on 3473** and **2.2% later on pinned main**. The shell itself arrives sooner on both servers. Main's cold downstream traffic falls **28.4%**.

With the new client held fixed, switching the sandbox server from 3473 to pinned main changes cold combined readiness from **11.100 to 3.597 s** (67.6% sooner) and downstream from **425,196 to 64,132 bytes** (84.9% less). Those are server-version comparisons. The same-server old/new-client comparisons above isolate the client revision and must remain visible alongside them. CandyWrapper already supported bounded snapshots and replay, so this fixture does not reproduce every improvement in Theo's browser benchmark.

## What CandyWrapper does with each change

T3 `v0.1.3-nightly.20261025.3669` contains every introducing commit in the audit registry, including the required fast-load protocol changes. The matrix measures exact upstream main `5b35402623`, not that published runtime. The measured older runtime 3473 remains supported. No installed runtime was changed. The [upstream audit](../research/t3-fast-load-upstream.md) gives commit membership and exact source citations for every row; the [implementation review](../research/fast-load-review-2026-10-25.md) covers state and lifetime guarantees.

| T3 change | CandyWrapper now | Older-server behavior |
| --- | --- | --- |
| Compressed HTTP bootstrap | Loads a cold bounded thread over HTTP, then tails its sequence on the socket; tries once per owner and falls back to a socket snapshot on failure. | Existing HTTP route works on 3473; missing or failed routes fall back. |
| Snapshot and replay body deduplication | Sends `dedupeBodies=1` / `acceptDedupedBodies`; restores text, files and subagent bodies before reduction/cache, using bounded arrival-order sources for stream references. | Unmarked full records decode normally. |
| Compact ID tables | Sends `compactIds=1` on bounded/history HTTP and `acceptCompactIds` on subscriptions; expands record IDs before typed decoding, preserving opaque tool/provider payloads. | Full string IDs remain valid. Both formats passed the sandbox matrix. |
| Omit idle subagent shells | Negotiates `shellThreadFamilies`, sends matching HTTP/socket omissions, and recovers families on demand. | Missing capability keeps the complete shell and avoids new recovery RPCs. |
| Omit older settled shells | Requires both shell flags; loads counts and tied-cursor pages as shelves open. Search, deep links, palette and composer mentions recover omitted rows. | Missing flags keep all rows locally. |
| Complete worktree ownership read | Uses the gated owner-list RPC before cleanup when shells are partial; failed reads keep the worktree. | Full-shell ownership checks remain available. |
| Smaller long/agent-turn windows and bounded SQL | Uses existing bounded/history APIs, preserves opaque cursors and ordinal watermarks, and accepts split turns. A UI cursor guard permits repeated pages inside one folded work log. | Keeps the old server's larger initial window and paging rules. |
| Slimmer thread controls, checkpoint reserves and fork ancestry shortcuts | Keeps required control records and uses bounded requests; server work benefits automatically. | No client-side imitation or database migration. |
| Shell SQL/index and reader routing | Benefits automatically from server reads with less work/contention. | Server implementation stays unchanged. |
| Cheaper shell resume and transcript suppression | Retains an authoritative in-memory cursor only with matching policy/version; accepts valid sequence gaps and snapshot fallback. Disk-only or changed-policy state bootstraps anew. | Existing replay works; no speculative omission flag. |
| Slow-client shell and thread event coalescing | Applies surviving events in transport order; restores deduped bodies before reduction, including replay. | Existing sequence and bounded-buffer behavior remains valid. |
| Config startup race fix | Shares one supervised config stream between shell negotiation and existing observers; no extra unary config read. | Existing config stream works and missing flags mean false. |
| WebSocket deflate and HTTP gzip | Already automatic in URLSession; confirmed actual negotiation on both sandbox versions. Compression predates the comparison base. | Both tested versions compress; no manual extension header or decompressor. |
| Existing lazy command output, diffs and handoff history | Keeps demand-driven RPCs and does not eagerly fetch omitted bodies individually. | Existing behavior. |
| Existing replay budgets and task/workflow controls | Keeps cursor/snapshot recovery and required non-window control rows. | Existing behavior. |
| Web-only decode/cache/render changes | Native off-main decoding and retained stores already cover part of this work. No new wire opt-in; cursor-only disk-write suppression and unrelated native render profiling remain separate work. | No compatibility change. |

## Sources and method

- Baseline core: `8c8e6d3026128894bd48b6d410320fdf0ab4c16b`, built from its own clean sparse checkout.
- New core: parent `341775ef141430f5cf1e9fcb6c7d371a95ecfb19`, including the shared config stream, descriptor-version warm resume, empty-overlay fast paths and cancelled-start guard. Both clients were rebuilt with the same revised harness. The source selection is recorded in each build's `client-commit.txt` and in the raw provenance.
- Integration later rebased that core to `dc24a374`, on top of main's separate Nightly wire-default changes. Its fast-load implementation is identical. The [source restoration patch](fast-load-2026-10-25/measured-core-rebase.patch), applied with `git apply --unidiff-zero` in a disposable checkout of `dc24a374`, restores all CandyKit production sources and its package manifest to the measured `341775ef` contents. It only reverses those four unrelated Nightly source files. The subsequent folded-history UI fix changes demand from the window, not this headless harness. The original binary/source hashes in provenance remain unchanged.
- Old server: the separate `0.1.2-nightly.20261021.3473` runtime, source `1688f965682d331da16a8c39f049592361f69c8d`. Nothing was installed into the user's runtime.
- New server: exact upstream main `5b35402623d7d1d88eaa472807272a6c2e78012a`, running from the existing independent Node source archive. All 2,058 retained blobs under `apps/server`, `packages/contracts`, `packages/shared` and `packages/client-runtime` were checked against that commit, with zero mismatches. Unused mobile, desktop, marketing and repository folders remain pruned; the server and its dependencies remain intact. No newer main or published runtime was substituted.
- Link: 400 decimal kbit/s aggregate in each direction, with 200 ms queued one-way latency, giving 400 ms RTT. The counting proxy delivers 50,000 bytes/s per direction. Its earlier persistent-HTTP calibration remains unchanged: two 100,000-byte bodies took 2.408 and 2.407 s, each with 100,043 downstream bytes including headers.
- Fresh client process, empty in-memory stores and no disk cache for each cold cell; servers stay warm. A second connection retains the same stores and cursors. Twelve cells run sequentially in three alternating orders. Both builds use Release and native SwiftPM with `-j 2`.

The executable links the actual CandyWrapper HTTP client, RPC socket, connection supervisor, thread loader, shell store and thread store. Only AppKit session orchestration is mirrored. Baseline config opt-ins match `8c8e6d30:App/Sources/ComposerController.swift:460-465`; lifecycle setup matches `App/Sources/ShellSession.swift:70-78`. The new fixed-server shell flow follows `341775ef:App/Sources/ShellSession.swift:165-216`. This measures data readiness and protocol synchronization, not UI first paint, layout, CPU, memory or energy.

**Both clients now include the app's existing config and lifecycle streams.** The new shell shares `ServerConfigFeed` with the config observer and issues no unary `server.getConfig`. On retained reconnect it reuses matching descriptor-version and omission policy without waiting for config. The initial diagnostic omitted these common boot streams in both clients and included an extra config read only in the new client. Its old-client numbers are a different workload: do not combine them with this final matrix or treat their difference as a controlled measurement of the config fix. The diagnostic and its raw artifacts remain separate in [the initial report](2026-10-25-fast-load-initial.md).

Ready means a projection has reached its store; both ready is the later of shell and thread. Synchronized waits for shell and thread completion markers plus the generation's initial config snapshot. Lifecycle traffic is included through that boundary. All table values are **median (minimum to maximum)** from three runs. Delivered TCP payload includes compressed bodies, HTTP/WS headers and framing; it excludes TCP/IP overhead, retransmissions and post-boundary traffic.

## Compression and complete-history checks

The proxy observed all twelve WebSocket upgrades per server negotiating `permessage-deflate`, with the matching request header. Every new cold run made exactly one shell GET and one bounded-thread GET. Those requests advertised `Accept-Encoding: gzip, deflate`, and their responses used `Content-Encoding: gzip`. There were six snapshot GETs per server across the three new-client runs and no repeated bounded GET or socket snapshot fallback needed for these successful bootstraps.

An untimed correctness stage followed each pair, paging history over the isolated direct origin. Its traffic is excluded from the constrained phase counters. All twelve results have **1,322 timeline rows, 482 visible message items and zero blank visible message items**. Paging took twelve pages on 3473 and fourteen on main. Every fully paged visible-message hash equals the synthetic source:

Composite visible-content hashes also match old/new within each server, both cold and fully paged. Every retained result exactly matches its own cold content and shell count. The fixture payload hash is `c869e9cb80b913c35c708fbd336316ac384404d57fc6adb49e7dd5457e341fef` in both homes. It contains 1,301 shell rows: 81 ordinary active threads, 1,000 old settled threads, 200 idle children and twenty active children. The big thread includes 600 tool/reasoning rows in its final agent-created run. No real turns, accounts or user history were used.

## Remaining regressions and limits

- Cold combined readiness and synchronization regress on both tested servers, despite earlier shell readiness. The thread is the bottleneck in the new path on this fixture and link. This report does not claim a faster first complete shell-plus-thread view.
- Main's downstream saving does not remove its cold thread delay. The protocol stages expose that tradeoff, but these runs do not isolate its internal causes.
- Cold upstream traffic rises on both servers; 3473 also has a small downstream increase. The retained 3473 synchronization median is 15 ms later, and retained upstream is slightly larger on both servers.
- This covers one deterministic synthetic fixture, one 400 kbit/s / 400 ms link, warm servers and three runs per cell. It does not exercise server-policy changes during a connection, failed-route fallback, deferred command-output fetches, rendering, disk-cache paint or process-cold server startup. App, full-suite and performance checks are recorded separately above; the matrix itself measures store readiness.

The quiet guard checks compiler, linker and test-runner processes before cells, every two seconds while a cell runs, and after cells. No overlap was detected in this accepted run. A previous attempt was aborted on overlap, preserved separately in the sandbox and excluded entirely; none of its cells were reused. The final run used the same source pins and unmodified fixture. Hashes and compression were validated before writing this report.
