# CPU of 1.20.0 against 1.19.0 (2026-11-26)

The user, on 1.20.0, saw the sidebar's CPU meter read 2.4%, 10% and 28% while a reply streamed into the open thread and several agents updated the sidebar, with Redesign and the inset panel on. They later added that turning the inset panel off changed nothing and that the number climbs while they just sit there.

In the sandbox, 1.20.0 costs the same as 1.19.0 in every state measured, and no state got near 10%. I found no regression and changed no code. The cost the user saw is real, because the meter's arithmetic matches `getrusage` exactly, but it depends on something the sandbox doesn't have: their thread count, their agents' event rate or their long threads. It is unmeasured here.

## Results

App CPU is the app's own CPU as a share of one core, from `proc_pid_rusage` before and after each window, like the meter. WindowServer CPU comes from the same counters read through `sudo`. Each run launched a fresh app, waited 12 s, then measured four 6 s windows. The two builds alternated, with the order reversed each round. Load averages ran from 2 to 24 while other agents compiled and tested.

## How it was measured

1. I built Release apps of `v1.19.0` and `v1.20.0` in their own worktrees, each with its own test bundle id, no update feed, and an ad hoc signature as `scripts/perf-review` does.
2. Both builds got the same measurement-only patch, which was never committed. It makes `CANDY_CLIENT_SETTINGS` work in Release, adds `--measure-terminal` to open the drawer 3 s after `--open-thread`, and adds `--measure-occlusion <file>` to log `occlusionState` changes.
3. Every run used `CANDY_THEME=candywrapper-dither`, `--appearance dark`, `redesignBackground` set to `dither`, or `flower` for the new-thread page, and the inset panel on, which is the default.
4. Covered windows hide drawing. The first run, launched with `--background`, logged `visible=false`. After the user freed the screen, every run in the table was launched in front under the screen lock and logged `visible=true`. Runs marked frontmost were also activated with `/tmp/cw-ui/front`, and `lsappinfo front` confirmed the app was active, so the account card's meter was sampling as it does for the user.
5. The working threads were full-access `claude-haiku-5-5` turns that ran `caffeinate -t 110` six times. Claude Code refuses a foreground `sleep`, and that refusal cost one turn. They show as working in the sidebar, with the working timer and dots, but send few events while each command runs.
6. Ten sandbox turns in all. One made the finished rest thread, one was the refused `sleep`, four were working threads, and four were streamed replies.

## The meter

`AppUsageReadoutView` adds `MACH_TASK_BASIC_INFO`, which counts threads that ended, to `TASK_THREAD_TIMES_INFO`, which counts live threads, and divides by uptime. I ran the same arithmetic next to `getrusage` across one second of main-thread work plus a thread that ended before the second reading. Both read 1.500 s over 2.01 s, 75%, so the meter shows the app's CPU accurately.

The meter samples every 5 s while the app is active, its window is visible and the sidebar is open. Frontmost at rest, the app read 0.04 to 0.06%, against 0.02% when not active. That is the meter's whole cost, at about 0.2 wakeups a second. It has to sample to show a number, so I left it.

## What stayed unmeasured

- 8 working threads. The ten-turn budget ran out at 4.
- Threads that stream text continuously while the open thread sits still. The working threads here spent their time inside a shell command, so they sent shell events every couple of minutes, not every few hundred milliseconds like a busy agent writing a long answer.
- The user's scale: hundreds of threads, several environments, long threads with large timelines. The sandbox has neither the thread count nor a thread long enough to scroll. `--open-thread "Numbers 1 to 1000"` matched nothing there, so my scroll runs scrolled nothing and are left out.
- A full `scripts/perf-review`. I stopped it after 10 minutes in its first quiet-machine wait, because other agents' `swift-build` and `swiftpm-testing-helper` processes ran the whole time. Each of its nine launches would have waited up to 10 minutes.
- Whether the inset card's rounded clip of the art, `masksToBounds` with `cornerRadius` over sublayers, costs the window server an offscreen pass per frame. The window server noise was larger than any difference between the builds, and the user reports that turning the inset off changes nothing.
