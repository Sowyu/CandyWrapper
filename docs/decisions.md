# Decisions

What the user decided and why, newest first. Check here before changing anything these cover.

- 2026-10-14, agent decision for the user's optimisation pass: no T3-style idle pings on direct routes. T3 pings every 5 s and drops a socket after 15 s without a frame (rpc/protocol.ts:10-12), which also turns any server stall over 15 s into a "reconnecting" banner. CandyWrapper checks a quiet socket only while a reply is owed or a thread runs on that environment and the app is active, and probes on wake, app activation and network changes. That catches a dead network during a turn within 14 to 16 s and costs 0.19 extra wakeups/s only while a turn runs; idle stays at zero. The price: an idle, frontmost window on a silently dead remote network keeps showing "Connected" until the next send, wake, activation, network change or turn. Revisit if the user reports stale idle windows (docs/perf/README.md, "Connection in bad moments").

- 2026-10-14: the user removed Glass Native (Experimental), shipped in v1.1.0: "remove native glass its useless". A stored Glass Native choice falls back to Glass. Fixes made during its work that apply to every theme stay.
- 2026-10-14: classic Glass takes the user's Origin technique: a pre-blurred copy of the desktop picture, lined up with the real wallpaper behind the window, instead of the live behind-window blur. The user offered it as "it might be better".
- 2026-10-14: CandyWrapper should not depend on T3 Code being installed ("i do kinda want candy wrapper to be independent of t3 code"). It installs and updates its own copy of T3's server runtime and starts that when no T3 server is already running for the home. This replaces the proposal below. Threads stay in the same T3 home, so the official app keeps seeing them.
  - Built 2026-10-14. Runtimes live in `~/Library/Application Support/CandyWrapper/Runtimes/versions/<version>/t3`, T3's own pinned runtime layout. `state.json` keeps the active version and the previous one, and every other version folder is deleted when one becomes active (`RuntimeStore`). An install downloads T3's published release from GitHub (`releases/download/v<version>/t3-<version>-darwin-arm64.tar.gz`, or `T3CODE_RELEASE_BASE_URL`), checks it against the release's `SHA256SUMS`, unpacks it with `tar` into a staging folder and renames it into place, as cloud/pinnedRuntime.ts does. Nothing is bundled in the app, and T3 publishes no Intel macOS build.
  - Order at startup (`RuntimeChoice`): a server already running for the home is reused as before, and a home T3's background service owns is still never started by us. Otherwise T3's installed runtime (`<home>/runtime/service-state.json`) when it is newer than ours, else ours, else an install of the version this client implements, with a progress toast. The Version row's update button installs the newer version into ours and restarts our server on it.
  - Downgrade guard (`HomeRecords`, in `Runtimes/homes.json`). T3's servers open a database a newer server migrated and only log a warning (persistence/Migrations.ts:198-221), so CandyWrapper refuses instead. The floor for a home is the newest of: the newest version CandyWrapper started there, T3's service `activeVersion` and pending update target, and, for `~/.t3`, the installed T3 Code app's version. A runtime below the floor never starts; CandyWrapper installs the floor version instead, and if that install fails it shows "CandyWrapper won't start T3 Code <v> …: T3 Code <floor> already used this data". After each start it also notes the newest `effect_sql_migrations` id the database holds (read only), and refuses a version whose noted migration is below the database's.
  - If the official T3 Code app is still installed and older than what CandyWrapper last ran on `~/.t3`, CandyWrapper can't stop that app: it would open a database a newer server migrated, and T3 only warns about that. The user should update T3 Code before opening it again. The reverse is safe: a newer T3 Code app raises the floor, so CandyWrapper installs that version rather than run an older one.
  - Development: `CANDY_RUNTIMES` moves the runtime folder (scripts/run-app passes it through, keep it under /tmp). A development home without it still runs the `t3` that run-app links, without a download.
- 2026-10-14, proposal, not yet confirmed: updating the server CandyWrapper starts on this Mac. That server runs `t3 serve` with T3's desktop bootstrap (`mode: "desktop"`, LocalServerLauncher.swift), so it advertises `serverSelfUpdate: "desktop-managed"` without `desktopAppUpdate` (ServerEnvironment.ts:196-206). T3 would answer "Update the desktop app on that machine", which is wrong here: updating CandyWrapper does not change the server. The server has no launcher to hand off to, and CandyWrapper picks the binary again on every start (the installed runtime's `t3`, else `t3` on `PATH`, LocalServerDiscovery.swift). So when the primary environment is CandyWrapper's own server and it is behind, the Version row reads "Update T3 Code on this Mac, then reopen CandyWrapper to restart its server." and the composer notice reads "Update T3 Code on this Mac", with no button. A server T3's background service runs (the usual case, and the user's) gets T3's real "Update" over `server.updateServerWithProgress`. Revisit if the user wants CandyWrapper to download runtimes itself, which would mean writing into a T3 home.

- 2026-10-10: T3 Connect sign-in route, final. The user left it to us ("whatever is best"). The CLI's OAuth token lists environments but can't connect (`dpop-token` only takes the `t3-relay` template JWT, `infra/relay/src/http/Api.ts:1020-1025,1638-1656`). CandyWrapper signs in natively through Clerk's Frontend API like T3's mobile app (docs/research/M-clerk-native.md): email code first, then password, native views, the Clerk client token in the Keychain, a fresh `t3-relay` JWT minted per relay call (60 s lifetime). No webview and no URL scheme. Left out: social OAuth (it would borrow T3's Android redirect `clerk://com.t3tools.t3code.callback` inside ASWebAuthenticationSession; ask the user before adding it) and passkeys (T3's associated domains list only T3's bundle ids). Risk: T3 can change its Clerk config; the durable fix is asking T3 to allowlist CandyWrapper.
- 2026-10-09: The app never starts a second server on a home that has one. `LocalServerDiscovery.discover` waits up to 20 s, then shows an error, when the runtime file names a live process that doesn't answer, or when T3's launch agent (`~/Library/LaunchAgents/com.t3tools.t3code.service.plist`, `T3CODE_HOME`) owns the home. On this Mac the service owns `~/.t3`, so the app only ever joins the live server there.

- 2026-10-09: Allow Remote Access (app menu). On keeps the app's own server running while CandyWrapper is idle, so the user's phone can reach this Mac. Off lets it stop after 10 idle minutes. Until the user picks, it follows whether T3 Connect is linked (`GET /api/connect/link-state`). Proposed to the user after they asked about reaching the Mac from Android; not explicitly confirmed.
- 2026-10-09: The app records the server it started (pid plus start time, and its own) in `~/Library/Application Support/CandyWrapper/owned-server.json`. On the next start, if that app process is gone, it stops exactly that server. Otherwise a crash would leave a server that later launches treat as someone else's and never stop.

- 2026-10-09: Server lifecycle on the user's laptop: CandyWrapper starts T3's server only when needed and stops it when idle or on quit, never during a running turn or a pending approval. It reuses an already-running T3 server instead of starting a second one, and launches its own server with the lowest-memory Node settings that measure fine. Claude agents keep running locally through it, and threads stay compatible with official T3. The launch shows cached sidebar state while the server starts.

- 2026-10-09: Webviews are allowed for the features that render web content in the official app (built-in browser and preview, HTML replies, MCP apps, Mermaid, HTML file preview, Clerk sign-in). Condition from the user: no background cost. Create the WKWebView only while its pane is visible, tear it down when hidden, never keep one alive or polling, and never load one at launch.
